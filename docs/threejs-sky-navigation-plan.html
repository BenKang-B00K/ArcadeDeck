Sky Navigation for ArcadeDeck

Three.js flight mode — each cloud is a gateway to a game. Planning doc + live prototype. docs/threejs-sky-navigation-plan.html

Verdict: buildable, ~2–3 days, one condition

Do not replace /. Home is a prerendered, SEO-load-bearing route (25 games × 6 locales of static shells from scripts/prerender-pages.js). Replacing it with a WebGL canvas deletes the crawlable content that ranks today, and costs an LCP element.

Ship sky mode as a second front door: route /sky, lazy chunk, opt-in button on Home, remembered in localStorage. Home stays as-is and keeps ranking. Zero SEO risk, zero bytes added to first paint.

Why scene.ts is not React

Three.js owns a mutable render loop. Wrapping it in React state = re-render storms. One useEffect mounts it, returns dispose(). No @react-three/fiber — that is another 60 KB and a reconciler you do not need for 25 static billboards.

Why DOM labels, not 3D text

Project each cloud's world position to screen coords, position an absolute <a>. Free text rendering, real fonts, real links, keyboard focusable, screen-reader readable, i18n via the existing getLocalizedString. A TextGeometry gives you none of that and costs a font loader.

3. Layout — genre archipelago, not a spiral

The core design question: what can a sky do that a grid cannot? Not density — a grid wins that. Not speed — a grid wins that too. The one thing a sky owns is spatial memory: "Tower Defense is past the sunset, Gem Merge is the low island on the left." A grid can never be remembered as a place.

That makes layout the highest-leverage decision in the whole feature. A golden-angle spiral by array index looks even but means nothing — position carries no information, so nothing is learnable and the sky is just a slower grid. Cluster by genre instead. Five islands on a ring, games spiralling inside their own island.

// raw genres give 11 zones, 7 of them a single game — dead sky. Fold into 5 dense islands.
const ZONE_OF = { Arcade:'Arcade', Casual:'Arcade', Strategy:'Strategy', 'Auto-Battle':'Strategy',
                  'Tower Defense':'Defense', Idle:'Idle & Tycoon', Tycoon:'Idle & Tycoon',
                  Action:'Action & RPG', Survival:'Action & RPG', Roguelike:'Action & RPG', RPG:'Action & RPG' };

const za = zoneIndex / ZONES.length * Math.PI * 2;                 // island centre on a ring
const centre = new Vector3(Math.cos(za) * 95, Math.sin(zoneIndex * 2.3) * 12, Math.sin(za) * 95);
const a = k * GOLDEN, r = 11 * Math.sqrt(k);                       // k = index WITHIN the island
pos = centre.add(new Vector3(Math.cos(a) * r, Math.sin(k * 1.9) * 6, Math.sin(a) * r));

Zone sizes land at Arcade 9 · Strategy 6 · Action&RPG 4 · Defense 3 · Idle&Tycoon 3 — every island substantial, none a lonely single cloud. Zones map onto the existing /genre/:slug IA, so the sky and the grid describe the same site.

Three properties worth protecting

  • Positions are deterministic — no Math.random() anywhere. Same sky every visit, or spatial memory never forms. This is a hard constraint, not a nicety.
  • Adding a game must not reshuffle the sky. Append within its zone (k = index within zone) so existing clouds never move. Sorting the whole array by date would relocate all 25.
  • The hole in the middle is the hub. The ring layout leaves an empty centre — that is where the ArcadeDeck logo / "exit to grid" portal belongs.

Status still tiers within a zone: badge:"NEW"|"UPDATE" nearest the island centre; status:"IN PRODUCTION" (4 games) on the island edge as dim translucent puffs, label COMING SOON, not clickable.

Zone banner — how it's built

Pure DOM + CSS on top of the existing label projection. No extra draw calls, no texture, no geometry — the sky is still 1 draw call with the banners on.

  • Bob happens in world space, not CSS. A CSS translateY keyframe would bob by a constant pixel amount whether the island is 40 or 140 units away, which instantly reads as a sticker on the screen. Offsetting the world-space Y before projecting means the motion foreshortens with distance and the banner stays welded to its island. ~12 px amplitude near, a slow 5.7 s period.
  • The stem is measured, not fixed. Both the banner anchor and the island centre are projected each frame; the stem's height is the screen-pixel delta between them. So the pointer actually lands on the island and shortens correctly as you approach, instead of being a fixed stub that detaches at range.
  • Hue per zone (cyan · violet · magenta · lime · azure) via a --zc custom property — one variable drives border, text glow, box glow, stem gradient and the diamond tip. Zones become identifiable by colour before the text is legible.
  • The sci-fi read is three cheap tricks: a clip-path cutting opposite corners, a repeating-gradient scanline wash, and a bright leading edge bar — all in one pseudo-element.
  • Fades out on arrival ((d-40)/40). Once you're inside an island the banner has done its job and would only occlude the game labels.
  • Reduced-motion is respected — the brightness pulse and the bob amplitude both go to zero. Banners stay fully legible, they just stop moving.

Artwork — PNG or not?

Short answer: not PNG. WebP. And the format is not where the quality actually comes from — spend the free wins first. Numbers below are real encodes of a representative 256² cloud sprite (RGBA, alpha required), measured with the sharp already in devDependencies:

Art stylePNGPNG (palette)WebP q80PNG vs WebP
Soft painterly — what cloud art actually looks like141.4 KB20.6 KB21.7 KB6.5×
Detailed puff with visible wisps160.1 KB38.0 KB42.5 KB3.8×
Heavy noise (worst case)163.9 KB45.6 KB58.0 KB2.8×

Two things fall out of that table:

  • Straight PNG is never the answer — 6.5× the bytes for identical pixels on exactly the art style a cloud uses. Soft gradients are PNG's worst case and WebP's best.
  • Palette PNG matches WebP on size and loses on quality. It gets there by quantising to 256 colours — and on a cloud the smooth alpha falloff is the entire visible surface, so that's precisely where banding shows. WebP keeps full 8-bit alpha at the same cost. WebP-only is already the rule in RULES.md; this is one more reason it's the right rule.

But format is the last decision, not the first. Ranked by quality per byte:

#MoveCostNote
1Per-instance roll + non-uniform squash0 bytes Every puff was the same circle billboarded the same way — 150 identical stamps. Rolling each one differently and squashing slightly breaks that instantly. DONE — live below
2Tint clouds toward their zone hue0 bytes Reuses the banner's --zc palette through the existing setColorAt path. Islands become identifiable by colour from across the sky. Do this before buying any art.
3One painted 256² WebP puff~22 KB Replaces the runtime canvas gradient. Best single quality-per-byte purchase — an irregular painted silhouette is the one thing a radial gradient fundamentally cannot fake.
4Game thumbnails on approach0 new assets The {slug}-360.webp variants already exist. This is the highest-impact art in the whole feature and it costs no production time — it's what makes cloud #7 Gem Merge instead of "another white blob". Load only for the ~6 nearest.
56-puff atlas~180 KB Measured, 768×512 WebP q80. Only if 1–4 still read repetitive. Note it nearly doubles the whole sky chunk budget and needs per-instance UV offsets (InstancedBufferAttribute + onBeforeCompile) to stay at one draw call. Real complexity — earn it before spending it.

Compression footnote: sprite cost is driven by how noisy the art is, not by resolution or format — the worst-case style costs ~2.7× the painterly one at the same size in the same encoder. Brief the artist for soft, large-feature shapes and the bytes take care of themselves.

Recommended combination

Do 1 + 2 + 3 + 4. Skip the atlas. Total new artwork: three cloud sprites. Total added weight: ~30–70 KB. Total added draw calls: 2.

Why the atlas is out: an atlas exists to keep everything in one draw call, which costs a per-instance UV attribute and an onBeforeCompile shader patch. But the budget allows 40 draw calls and we are using 1. Three separate textures on three InstancedMeshes buys the same variety for 3 draw calls, zero shader work, and fewer bytes (no atlas padding, and three small images compress better than one big sheet). Cheaper on every axis that matters. DONE — the prototype now runs 3 variants at 3 draw calls

Artwork brief — three sprites

Generate white cloud on pure black, square, 1024×1024. Image generators cannot emit a real alpha channel, so brightness becomes transparency: scripts/sky-puff-textures.cjs keys luminance to alpha and encodes to WebP at 256².

node scripts/sky-puff-textures.cjs raw/puff-a.png raw/puff-b.png raw/puff-c.png
# -> public/images/sky/puff-{a,b,c}.webp   (256², alpha, sRGB, reports KB and warns over budget)

Non-negotiables — these are what make the sprite work in-engine rather than just look nice:

  • Pure black background (#000000), not dark grey, not a sky. Grey background becomes a translucent square halo around every cloud.
  • Neutral white cloud, no colour cast. The engine multiplies in the zone hue at runtime — pre-tinted art fights it and the islands stop being colour-coded.
  • ~10% empty margin on all sides. A cloud touching the frame edge gets a hard straight cut where the sprite ends.
  • Soft, large forms. Fine wispy detail is the single biggest driver of file size — the noisy style measured 2.7× the painterly one.
  • No horizon, ground, sun, birds, text, watermark, border, or drop shadow. One isolated cloud mass.

Open question worth a decision

Should sky mode ever be the default? Recommendation: no, not initially. Ship it opt-in, then read the numbers — if sky-mode sessions show higher games-per-session than grid sessions, promote it to default for returning visitors only (first-time visitors keep the grid, which is also what search traffic lands on). That keeps the SEO surface and the acquisition path untouched either way.

What the prototype proves

  • 25 clouds place into 5 legible islands with no manual positioning and no overlap
  • Proximity targeting reads without a tutorial; autopilot crosses the sky in ~3.5 s
  • DOM labels track 3D positions at 60 fps and stay clickable / focusable
  • Neon zone banners bob in world space and their stems stay locked to island centres at any range
  • Whole sky is 150 instanced puffs across 3 texture variants, 3 draw calls, 0 downloaded assets — swapping the runtime placeholders for real WebP art changes one function, nothing else
  • Left alone with no input it never strands you — the boundary banks you back into the field

What it deliberately skips

Touch controls, reduced-motion, WebGL fallback, i18n titles, status tiering, and every tier-2 item above. None change the feasibility answer.
